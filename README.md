# Career Quest

Career Quest — демонстрационный карьерный навигатор по кейсу HackAlem AI / Halyk Bank. Сотрудник видит профиль, требования следующего грейда и 1–3 доступных шага развития с объяснением. После завершения активности навыки и готовность к цели пересчитываются. HR видит общие разрывы, сотрудников без подходящего шага и статистику участия, а также может загрузить проверочные данные жюри.

Данные синтетические. В качестве «сегодня» используется дата среза набора — **2026-10-01**, даже если системная дата другая. Это делает демонстрацию воспроизводимой и сохраняет будущие сессии из каталога событий.

## Быстрый запуск для жюри

Нужны Docker Desktop / Docker Engine с Compose и свободный порт `3000`. OpenAI-ключ для запуска **не обязателен**: без него сервер использует воспроизводимое ранжирование и честно показывает режим «Умный подбор».

```bash
git clone https://github.com/BAITC-Hacks/hack-f02d3fd7-a-b-systems.git
cd hack-f02d3fd7-a-b-systems
cp .env.example .env
docker compose up --build -d
```

В Windows PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env`. Откройте **http://localhost:3000**. Код входа на HR-экран для локальной демонстрации берётся из `HR_ACCESS_CODE` в созданном `.env`. Перед доступом с других машин замените значения `POSTGRES_PASSWORD` и `HR_ACCESS_CODE` на свои. Не добавляйте `.env` в Git.

При первом запуске API самостоятельно применяет `server/schema.sql`, создаёт таблицы и импортирует стартовый набор: 200 сотрудников, 40 событий, 60 навыков, 32 профиля ролей и 2743 записи участия. Повторный запуск сохраняет новые данные в Docker volume.

```bash
docker compose ps
docker compose logs --tail=30 app
```

В журнале ожидается `Seeded 200 employees, 40 events and 2743 history rows`, затем адрес сервера. Остановить проект: `docker compose down` (данные PostgreSQL сохраняются).

## Что реализовано по ТЗ

| Сценарий | Где проверить |
|---|---|
| Профиль, роль, грейд, стаж, навыки, история, цель | Экран «Обзор», переключатель сотрудников и вкладка «История» |
| Карьерная траектория | Вкладка «Моя траектория»: требования целевого грейда, критичные разрывы и готовность |
| 1–3 рекомендации и объяснение | Блок «Ваши следующие шаги»: прирост навыков, цель, история, формат и ближайшая сессия |
| Пересчёт после `completed` | Кнопка «Отметить выполненной»; траектория и история обновляются сразу |
| HR-view | Частые skill gaps, сотрудники без шага, участие и статусы по активностям |
| Дополнительные данные жюри | HR → «Загрузить проверочные данные»; `employees.json` и/или `activity_history.csv` |
| Запрет mandatory/compliance | Отсекаются до AI-ранжирования и повторно проверяются при выполнении |

### Как выбираются активности

1. Сервер берёт явную `career_goal`, если она есть и соответствует профилю роли; иначе следующий грейд той же роли. Для `Lead` без новой цели используется текущий профиль.
2. Уровни навыков рассчитываются от последней оценки (`last_review_date`). Завершённые **после** неё активности применяются по хронологии. Это исключает двойной учёт более старых завершений.
3. Для каждого навыка вычисляется разрыв `max(0, required - current)`. Критичные навыки целевого профиля имеют повышенный вес.
4. Сервер исключает `mandatory`, `compliance`, события не для текущих роли/грейда, неудовлетворённые `prerequisites`, прошедшие сессии, уже завершённые события (кроме повторяемого клуба `EV_036`), а также события `in_progress`.
5. Оставляются только события с реальным полезным приростом: `new = max(current, min(5, max_level, current + gain))`. Ранжирование учитывает закрываемые критичные и обычные разрывы, завершённые мероприятия такого типа, а также `no_show`, `declined`, `dropped` по конкретному событию и повторные неявки на тот же формат.
6. При наличии `OPENAI_API_KEY` сервер отправляет **только допустимый shortlist** в [OpenAI Responses API со Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Модель выбирает 1–3 ID; ответ сверяется с shortlist. Таймаут — 7 секунд. При ошибке API или отсутствии ключа используются первые три результата расчётного ранжирования. Объяснение строится сервером из проверенных чисел, а не из неподтверждённых утверждений модели.

Формула готовности: `round(100 × (1 − сумма оставшихся разрывов / сумма требуемых уровней))`. Она показывает прогресс по навыкам; автоматического присвоения грейда нет.

## Архитектура и технологии

```text
React + Vite + TypeScript (порт 5173 при разработке)
              │ /api
              ▼
Express + TypeScript (порт 3001)
  ├─ правила допуска и расчёт траектории
  ├─ OpenAI Responses API (при наличии ключа)
  ├─ импорт JSON/CSV и HR API
  └─ PostgreSQL 16 / Supabase PostgreSQL
```

Сборка Docker отдаёт frontend и API с одного адреса `:3000`. Запросы к БД параметризованы; импорт происходит в транзакции. HR API требует серверный код `HR_ACCESS_CODE` через заголовок `x-hr-code`. Это упрощённая защита для демонстрации, не корпоративная система аутентификации.

| Путь | Назначение |
|---|---|
| `src/` | React интерфейс, стили и состояния экранов |
| `server/index.ts` | REST API, завершение активностей, HR-метрики |
| `server/domain.ts` | Чистые функции расчёта навыков, разрывов, траектории и рекомендаций |
| `server/ai.ts` | Запрос к OpenAI, проверка ответа и fallback |
| `server/db.ts`, `server/schema.sql` | PostgreSQL, миграция и первоначальный импорт |
| `server/import.ts` | Проверка и транзакционный импорт файлов жюри |
| `data/` | Исходные `employees.json`, `events.json`, `skills.json`, `activity_history.csv` и три README датасета |
| `scripts/smoke.mjs` | Сквозная проверка API с синтетическим проверочным профилем |
| `compose.yaml`, `Dockerfile` | Запуск приложения и PostgreSQL |

## Настройка `.env`

Создайте `.env` из `.env.example`. Это локальный файл и он исключён из Git. В репозитории нет настоящих ключей, токенов, паролей или строки подключения.

| Переменная | Когда нужна | Значение |
|---|---|---|
| `POSTGRES_PASSWORD` | Docker Compose | Локальный пароль пользователя PostgreSQL; замените шаблон |
| `HR_ACCESS_CODE` | Всегда | Код HR-экрана; замените шаблон |
| `DATABASE_URL` | Запуск без полного Docker Compose | URI внешнего PostgreSQL / Supabase или локальной БД |
| `PORT` | Локальный backend | По умолчанию `3001` |
| `OPENAI_API_KEY` | Режим OpenAI | Ключ только в `.env`, никогда в frontend |
| `OPENAI_MODEL` | Режим OpenAI | По умолчанию `gpt-4.1-mini`; можно выбрать доступную модель |

В Docker Compose приложение получает отдельные `PGHOST`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` и не требует `DATABASE_URL`. Пароль в URI для внешней БД должен быть URL-кодирован, если содержит специальные символы.

## Установка с локальным Node.js и PostgreSQL / Supabase

Требования: Node.js **22+**, npm, PostgreSQL **16+** либо проект Supabase PostgreSQL. Для отдельного frontend/backend при локальной разработке:

1. Создайте базу PostgreSQL и пользователя с правом создавать таблицы. Для Supabase создайте проект и возьмите строку подключения из настроек Database (при необходимости Session Pooler).
2. Скопируйте `.env.example` в `.env`, задайте `DATABASE_URL` и `HR_ACCESS_CODE`. `POSTGRES_PASSWORD` в этом варианте не используется. При подключении Supabase используйте предоставленные сервисом параметры TLS/URI.
3. Установите зависимости и запустите оба сервера:

```bash
npm ci
npm run dev
```

Frontend: **http://localhost:5173**. Vite проксирует `/api` на backend **http://localhost:3001**.

Миграция `server/schema.sql` выполняется автоматически при запуске backend через `initializeDatabase()`. При пустой таблице `employees` загружается датасет из `data/`. Если нужно применить схему вручную до запуска:

```bash
psql "$DATABASE_URL" -f server/schema.sql
```

В PowerShell используйте `psql $env:DATABASE_URL -f server/schema.sql` после загрузки переменной окружения. Обычный `npm run dev` читает локальный `.env` сам. Повторная инициализация не стирает импортированные профили и историю.

Проверка production-сборки и запуск без Vite:

```bash
npm run build
node --env-file=.env dist/server/index.js
```

Здесь backend раздаёт `dist/client` по `http://localhost:3001`.

## Сценарий демонстрации

1. Откройте приложение и в переключателе сотрудников выберите `E0028` — **Akmaral Ismailova**, `Backend Engineer`, `Middle`. У неё нет явной цели, поэтому система показывает путь до `Senior`.
2. На «Обзоре» найдите карточки рекомендаций. В демо без ключа строка источника — «Умный подбор»; с работающим ключом — «OpenAI recommendation». Каждая карточка показывает уровень навыка до и после, связь с целевым грейдом, историю и ближайшую сессию.
3. Перейдите в «Моя траектория»: видны требования `Senior`, текущие уровни и критичные навыки. На «Истории» видны `completed`, `no_show`, `declined`, `dropped` и другие статусы.
4. Нажмите **«Отметить выполненной»** на доступной рекомендации. После ответа API карточка исчезнет (исключение — регулярный `EV_036`), история пополнится `completed`, уровни по `gain/max_level` и процент готовности обновятся.
5. Откройте «HR аналитика», введите `HR_ACCESS_CODE` из вашего локального `.env`. Проверьте частые gaps, список людей без следующего шага и таблицу участия по событиям.
6. Внизу HR-экрана загрузите один или оба файла в формате исходного набора. Затем выберите нового сотрудника через переключатель и проверьте рекомендации. Импорт по `employee_id`/`record_id` обновляет совпадающие записи, новые добавляет; неизвестные роли, навыки или события отклоняются.

Проверочные данные могут иметь собственные ID. `employees.json` принимает объект `{ "employees": [...] }` как в стартовом наборе или массив профилей; CSV использует исходные десять колонок. Если CSV ссылается на нового сотрудника, загрузите профиль и историю одним запросом. Лимит каждого файла — 8 МБ. Точные поля и статусы описаны в `data/README.ru.md` (также есть английская и казахская версии).

## Автоматические проверки

```bash
npm test
npx tsc -p tsconfig.json
npm run build
npm audit
```

`npm test` проверяет допуск на всех 200 исходных сотрудниках, рост после `completed`, сценарий с критичным System Design против трёх неявок на Public Speaking и проверку ID из mock-ответа OpenAI. При запущенном Docker Compose сквозной тест проверяет импорт, 1–3 рекомендации, завершение, изменение навыков и HR API:

```bash
node --env-file=.env scripts/smoke.mjs
```

Тест создаёт новый синтетический профиль с уникальным ID в локальной БД при каждом запуске.

## Известные ограничения

- Нет SSO и настоящей аутентификации сотрудников: переключатель профилей открыт для демонстрации. HR-код — только барьер демо-стенда. Для эксплуатации нужны корпоративный IdP, роли на сервере, аудит доступа и политика доступа к персональным данным.
- Без `OPENAI_API_KEY` AI-вызов не выполняется, применяется прозрачное расчётное ранжирование. Реальный вызов OpenAI нельзя проверить без действующего ключа и доступа аккаунта.
- Дата каталога фиксирована на `2026-10-01`; после последних указанных сессий запланированные события без новых дат перестанут быть доступными. Self-paced события остаются доступными.
- Завершение активности в демо подтверждается нажатием кнопки. В рабочей системе статус должен поступать из LMS/HRIS или подтверждаться ответственным лицом.
- Процент готовности отражает покрытие требований по навыкам, но не заменяет аттестацию или решение о повышении.
- Интерфейс русскоязычный; исходные названия навыков и событий сохранены на английском, как в датасете.
